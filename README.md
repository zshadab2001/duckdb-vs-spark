# DuckDB vs Spark — where does the line actually sit?

A like-for-like timing comparison of **46 data operations** run on one ordinary machine, using
two engines: **DuckDB**, which runs inside a single process, and **Apache Spark**, which is
built to spread work across many machines.

All the data is synthetic and generated by the notebooks themselves. There is nothing here
from anybody's company.

---

## The question

> Spark is a **delivery company**. DuckDB is **your own kitchen**.
>
> For a big catered event you call the delivery company. For a sandwich you walk to the kitchen.
> Nobody thinks the kitchen replaces the caterers — but nobody orders a catering van for a
> sandwich either.

The interesting question is not which engine is better. It is **which jobs sit on which side of
the line** — and that has a measurable answer.

## The finding

Not "DuckDB is faster". That is a boring claim and an easy one to argue with.

The finding is that **the gap varies enormously depending on what the job does.** A row count
and a wide shuffle join are not the same kind of work, and treating them as though they need
the same tool is where the cost hides.

## The rules

1. **Same data.** Both engines read the same Parquet files from the same folder.
2. **Same names.** Tables are registered under identical names in both, so **most cases send
   the identical SQL string to both engines**. Where that is impossible, the case is marked and
   both versions are shown.
3. **Same budget.** Both engines get exactly the same memory and thread count. This is the most
   important fairness rule in the project.
4. **Warm-up first.** One untimed run before the clock starts, so a cold JVM is never timed.
   That is generous to Spark on purpose.
5. **Startup excluded.** Spark's start-up time is reported but never added to a benchmark.
   Every timing is work only.
6. **Answers are checked.** Both results are compared. A fast wrong answer is worthless.
7. **Spark is tuned.** Every Spark setting changed from its default makes Spark **faster** —
   notably `shuffle.partitions` (Spark's default of 200 is a disaster on one machine) and Arrow
   for result handover. All of them are visible in [`bench/config.py`](bench/config.py).

## The data is dirty on purpose

Data-quality checks on perfectly clean data measure nothing. So the generator plants defects
and lists them, rather than leaving anyone to guess:

* ~2% null customer IDs, ~1% null amounts
* ~0.5% exact duplicate rows
* ~0.5% negative amounts (invalid)
* ~1% of rows pointing at customers who do not exist
* inconsistent country text — `'UK'`, `'uk'` and `' Uk '`
* a JSON column, a wide text column, and 22 columns in total

## What this deliberately does **not** show

Stated up front, so nobody has to go looking for it:

* **Spark's actual benefit.** Spark exists to use many machines. Everything here ran on one.
  So this measures the **cost** of distributing work, not the payoff.
* **A crossover point.** On a machine this size the crossover is not reachable, and guessing at
  one would be dishonest. Notebook 09 measures something real instead — the memory at which a
  single machine **stops working** — and gives a scaling rule you can check.
* **Anything about your data, your cluster or your costs.** The data here is invented.
* **Governance, sharing, access control or streaming.** All real reasons to run a platform,
  none of them measured here.

## Running it

### On GitHub Actions (no setup at all)

Go to the **Actions** tab → **Run benchmark** → **Run workflow**.

It runs on a clean machine, executes every notebook, and attaches an **HTML report** you can
download. The run page records the exact machine, the commit and the timestamp.

Anyone can press that button. That is the point — a benchmark someone else can re-run beats one
they have to take on trust.

### In GitHub Codespaces

Open the repo → **Code** → **Codespaces** → create. The devcontainer installs Python, Java and
everything else. Then run the notebooks in order.

Remember to **stop** the Codespace when you finish; closing the tab does not stop it.

### On your own machine

```bash
pip install -r requirements.txt          # DuckDB alone is 2 MB; the rest is for Spark
cd notebooks
jupyter lab                              # then run 00 first, the rest in order
```

Java 17 or newer is required **for Spark only**. DuckDB needs nothing.

### Settings

Everything lives in [`bench/config.py`](bench/config.py), overridable by environment variable:

```bash
BENCH_QUICK=0        # full run instead of the quick check
BENCH_THREADS=4      # threads per engine
BENCH_MEM_MB=4096    # memory per engine, in MB
```

**If you think a setting is unfair to either engine, change it and re-run.** That is what the
file is for.

## Rough guide to picking

| Reach for **DuckDB** when… | Stay with **Spark / Databricks** when… |
|---|---|
| The job reads gigabytes, not terabytes | The job reads terabytes |
| One job or one person at a time | Many people sharing one cluster |
| Someone is exploring, in a notebook | Streaming or live data |
| A scheduled transform or quality check | Two enormous tables joined together |
| Tests and pipeline checks | You need the catalog, permissions and governance |
