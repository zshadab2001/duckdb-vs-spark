# Does this job need more than one machine?

46 data operations, each run twice over the same Parquet files: once in a single process using
DuckDB, and once through Apache Spark, an engine built to spread work across many machines.

All the data is synthetic and generated by the notebooks themselves.

## The question

Not which engine is better. For each piece of work:

> **Does this job need more than one machine?**

## What splitting a job across machines does

Splitting a job across machines **adds extra work**. The job has to be cut into pieces, the
pieces handed out to different machines, data moved between them over the network, and the
answers collected and stitched back together at the end. None of that work exists if the job
just runs in one place.

It also **adds machines**. Ten machines instead of one means ten sets of cores and ten lots of
memory, all working at the same time.

On a big job the extra machines finish so much sooner that the extra work is well worth doing.
That is why Spark exists and why it is the right answer for a whole class of problems.

**Here there is only one machine, so there is only the extra work.** Spark still cuts the job up,
still moves data around, still stitches the answers back together, but there are no extra
machines to gain anything from. That is a deliberate limit, and it is exactly the position of a
job that never needed more than one machine: it does all the extra work, every time it runs, and
there was never anything to gain from it.

**Two things differ at once, and this cannot separate them.** Spark splits the work up, and it is
also a different engine: it runs on the JVM with a scheduler, against a C++ engine running inside
this process. Part of every gap below comes from the splitting and stitching, and part of it
comes from the two engines simply being built differently. This setup cannot say how much is
which, which is why the tables show a plain ratio and do not label it as the price of splitting.

What can be said without stretching it: these jobs ran faster in one process, and the split-up
version did all the extra work with no extra machines to show for it.

## The finding

The gap varies enormously depending on what the job does. A row count and a wide shuffle join
are not the same kind of work, and treating them as though they need the same tool is where the
waste hides.

| `10_summary` | Everything combined |

## The rules

1. Both engines read the same Parquet files from the same folder.
2. Tables are registered under identical names in both, so most cases send one identical SQL
   string to each. Where that is impossible the case is marked and both versions are shown.
3. Both engines get the same memory and thread count.
4. One untimed warm-up runs first, so a cold JVM is never measured.
5. Spark's startup time is reported but never added to a timing.
6. Both results are compared. A fast wrong answer is worthless.
7. Every Spark setting changed from its default makes Spark faster, notably
   `shuffle.partitions` (the default of 200 schedules 200 tasks across a handful of cores) and
   Arrow for result handover. All of them are in [`bench/config.py`](bench/config.py).

## What this cannot answer

Where the crossover is. Finding that needs the other half measured, the part where extra machines
actually help, and that needs real machines, real data and real hardware. And as above, it cannot attribute the gap to distribution
alone, because the two engines differ in more than one way.
